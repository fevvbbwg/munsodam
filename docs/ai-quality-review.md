# AI 답변 점검 기록

문서담의 AI 품질을 설명할 때는 검색, 생성, 검증, 보류를 구분합니다. 임베딩과 LLM은 로컬 Ollama의 `embeddinggemma`, `qwen3:4b-instruct`를 사용합니다. 검색된 문장만 모델에 전달하고, 응답의 출처 ID·수치·기한·조건을 서버에서 다시 확인합니다.

## 2026-11-09 추가 점검

[`evaluation/docs/`](../evaluation/docs/)의 가상 문서 3개를 별도의 임시 SQLite 계정에 등록하고 실제 `/api/chat`과 두 지정 모델을 호출했습니다. 아래 다섯 질문은 기존 36문항 골드 회귀 세트와 별개입니다. 사람이 답변 본문과 출처를 확인했으며, 새 질문에 맞춰 코드를 수정한 뒤 다시 실행했습니다. [질문 원본](../evaluation/challenge/portfolio_smoke_questions.json)과 [실행 결과](../evaluation/results/portfolio_smoke_20261109_200438.json)를 공개합니다. 검색·답변·출처는 답변 가능한 4/4, 보류는 1/1이었고 중앙 응답 시간은 1,228.2ms였습니다. **독립 블라인드 평가나 성능 추정치는 아닙니다.**

| 질문에서 확인한 상황 | 수정 후 관찰된 응답 |
| --- | --- |
| “복귀 **전** 7일”이라는 잘못된 전제 | “복귀 **후** 7일 이내”로 정정, 출장비 문서 인용 |
| 식비 한도를 30,000원이라고 제시 | 실제 한도 25,000원으로 정정, 출장비 문서 인용 |
| 분실 노트북의 신고 시점과 대상 동시 질문 | 1시간 이내, IT 담당자와 관리자라고 답하고 기기 보안 문서 인용 |
| 문서에 없는 급여일과 있는 출장 정산 기한을 동시에 질문 | **전체 답변 보류**, 출처 없음 |
| 회사 자료의 개인 클라우드 저장 허용 여부 | 업로드 금지라고 답하고 기기 보안 문서 인용 |

복합 질문에서 처음에는 급여일을 “문서에 명시되지 않았다”고 추측하면서 출장 정산만 답했습니다. 원문에는 급여일에 관한 명시적 미기재 문장조차 없으므로 이 문장은 근거가 없습니다. 답변 검증기가 `명시되어 있지 않다`, `명시되지 않음`, `확인할 수 없다` 같은 미기재 표현도 감지하고, 인용 원문에 같은 항목의 명시적 미기재 근거가 있을 때만 허용하도록 고쳤습니다. 근거가 없으면 전체 답변과 출처를 보류합니다. 이 사례를 [서버 회귀 테스트](../server/tests/test_answer_fallbacks.py)에 추가했습니다.

## 서로 다른 문서의 규정이 충돌할 때

2025년과 2026년 가상 규정에서 출장 식비는 하루 20,000원·30,000원, 출장 정산은 복귀 후 5일·7일로 서로 다르게 적었습니다. 연도를 빼고 식비나 정산 기한을 물은 첫 실행에서는 모델이 한쪽 값만 골라 답했습니다. 개인 USB 저장도 한 문서는 허용하고 다른 문서는 금지하지만 첫 실행은 2026년 규정만 답했습니다. [초기 수치 결과](../evaluation/results/conflict_v13_20261109_205244.json), [초기 허용 결과](../evaluation/results/permission_conflict_v14_20261109_205530.json)를 남겼습니다.

이후 검색된 **서로 다른 문서의 같은 항목**에서 가까운 근거가 서로 다른 값이나 허용 방향을 말하는지 확인합니다. 연도를 질문에 넣거나 검색 범위를 문서 하나로 좁히지 않았다면 답변을 보류하고 적용 기준을 묻습니다. 이때 두 문서의 원문을 `conflicting_sources`로 따로 전달하며, 답변 근거 `sources`는 비워 둡니다. 한 연도를 지정하면 해당 규정을 답하고, 두 연도를 비교하면 각 연도의 근거를 따로 검색해 두 답과 출처가 모두 있는지 확인합니다. 웹 화면에서는 충돌한 원문 카드를 ‘답을 찾지 못함’과 구분해 표시합니다.

수정 후 [금액·기한 8문항 결과](../evaluation/results/conflict_v13_20261109_212636.json)는 답변·출처 6/6, 충돌 보류·원문 표시 2/2였고, [허용·금지 4문항 결과](../evaluation/results/permission_conflict_v14_20261109_212649.json)는 답변·출처 3/3, 충돌 보류·원문 표시 1/1이었습니다. 비교 답변에서 2025년과 2026년의 값이나 허용 방향을 서로 바꾸면 서버가 거부하고, 평가도 연도별 값의 연결을 따로 채점합니다. 기존 [골드 36문항](../evaluation/results/gold_20261109_212206.json)과 [개발 12문항](../evaluation/results/dev_20261109_212054.json)도 다시 통과했습니다. 모두 직접 만든 소규모 자료에 대한 회귀 결과입니다.

## 읽어야 할 한계

- [골드 36문항 보고서](../evaluation/results/gold_20261109_212206.json)의 100%는 직접 만든 작은 문서와 반복 사용한 문항에 대한 회귀 결과입니다. 실제 기업 문서나 새로운 주제에서 같은 성능을 보장하지 않습니다.
- 추가 점검은 직접 작성한 5문항·TXT 문서 3개, 충돌 점검은 12문항·TXT 문서 4개에 한정됩니다. 실제 문서의 복잡한 개정 이력, PDF 레이아웃과 표, 대규모 검색 집합은 별도로 평가해야 합니다.
- 수치·조건 검증은 규칙 기반 보완입니다. 한국어 문장의 모든 의미 관계를 증명하는 검증기가 아니므로, 중요한 판단에는 원문 출처 확인이 필요합니다.
- CI는 모의 모델 응답으로 회귀를 확인합니다. 로컬 Ollama 실호출 평가는 별도로 실행해야 하며, CI 성공을 모델 품질 검증으로 읽으면 안 됩니다.

평가 자료, 채점 정의, 이전 실패와 개선 기록은 [평가 안내](../evaluation/README.md)와 [프로젝트 사례 문서](portfolio-case-study.md)에 있습니다.
