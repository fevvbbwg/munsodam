# 문서담 — 실행 및 기술 참고

PDF·DOCX·TXT 업로드·목록·삭제부터 `embeddinggemma` 의미 검색, 근거 기반 `qwen3:4b-instruct` 답변, 답변 분량 조절, 출처 카드와 보류 응답, 골드 질문 평가까지 로컬에서 실행하는 웹 서비스입니다. 외부 유료 AI API는 사용하지 않습니다.

검색 기록과 저장한 근거는 계정별 브라우저 저장소에 남아 다음 방문 때 이어볼 수 있고, 답변은 근거 위치와 원문 링크를 포함한 Markdown 파일로 저장할 수 있습니다.

## 실행 환경 준비

- Docker Desktop 실행
- Ollama 실행 (Windows: `ollama serve`, 이미 Ollama 앱이 실행 중이면 생략)
- Node.js 22 (로컬 웹 개발 시)
- Python 3.12 (Docker 없이 로컬 개발 시)
- Ollama `0.11.10` 이상 권장
- 모델 준비:

```powershell
ollama pull qwen3:4b-instruct
ollama pull embeddinggemma
```

프로젝트 루트에서 실행:

```powershell
Copy-Item .env.example .env
docker compose up --build
```

- 웹 화면: http://localhost:5173
- API 문서: http://localhost:8000/docs
- API 생존 확인: http://localhost:8000/api/health
- 준비 상태: http://localhost:8000/api/ready

`/api/health`는 API 프로세스 생존만 확인하고, Compose의 웹 컨테이너는 이 경로가 응답한 뒤 시작합니다. `/api/ready`는 DB와 pgvector 연결을 확인하고, Ollama 버전/지정 모델 설치 여부 및 짧은 생성·임베딩 요청을 확인합니다. 여러 탭의 동시 준비 확인은 20초간 공유하며, `?force=true`를 붙이면 캐시를 건너뛰어 다시 검사합니다. 임베딩 차원이 768이 아니면 정상으로 표시하지 않습니다. 검색 API `/api/search`는 `vector`, `keyword`, `hybrid` 방식을 제공하며, 답변 API `/api/chat`는 vector 검색 근거만 사용합니다. 하이브리드는 키워드·벡터 순위를 RRF(k=60)로 결합합니다. 의미 검색 결과는 `MAX_COSINE_DISTANCE` 경계 밖의 구간을 화면에 노출하지 않으며, 하이브리드 검색은 질문 단어의 절반 이상이 일치하는 구간을 이 경계와 별도로 보존합니다. 한 단어만 우연히 겹치는 결과가 검색 근거처럼 보이는 일을 줄이기 위한 기준입니다. 결과에는 단어 일치 또는 내용 유사 표시를 붙여 검색 이유를 구분합니다. 키워드 검색은 문서에 실제로 일치하는 단어를 기준으로 보여줍니다. 문서의 명령문은 신뢰하지 않는 내용으로 전달하며, 출처는 검색 결과 ID와 대조해 서버가 구성합니다. 지정 모델이 없으면 다른 모델로 대체하지 않습니다. `OLLAMA_BASE_URL`은 `localhost`, loopback 주소 또는 Compose용 `host.docker.internal`만 허용해 모델 요청이 외부 호스트로 향하지 않도록 합니다.

여러 문서 주제를 한 번에 묻는 질문은 항목별로 근거를 확인하며, 한 항목이라도 근거가 부족하면 전체 답을 보류합니다. 질문 안에서 쉼표나 줄바꿈으로 나열한 주제 뒤에 공통 확인 기준을 붙인 경우에도 각 주제에 기준을 연결해 따로 검색합니다. 같은 주제의 속성을 연결한 표현은 한 질문으로 유지합니다. 서로 다른 연도에 같은 규정의 값이 다르면 연도 없는 질문을 보류하고, `/api/chat`의 `conflicting_sources`에 충돌한 두 원문을 별도로 반환합니다. 두 연도를 비교하는 질문은 연도별 근거와 답변 값을 대조합니다.

## 계정과 로그인

이메일 가입·로그인은 서버가 보관하는 HttpOnly 세션 쿠키를 사용합니다. 비밀번호는 PBKDF2 해시로 저장하고, 문서 목록·업로드·다운로드·검색·삭제를 계정 소유자로 제한합니다. 현재 `data/local.sqlite3`에 저장된 기존 문서는 첫 번째로 만든 계정에 연결해 유지하고, 이후 가입한 계정은 별도의 문서함을 사용합니다. 로그인 아이디는 가입 이메일입니다. 로그인 화면의 아이디 찾기에서 미리 발급한 복구 코드로 이메일을 확인할 수 있고, 로그인 뒤 계정 관리에서 비밀번호 변경과 복구 코드 발급을 할 수 있습니다. 메일 재설정 링크는 30분 동안 유효하고 한 번만 사용할 수 있습니다. 복구 코드는 아이디 확인에는 소모되지 않으며, 비밀번호 재설정에 사용하면 폐기됩니다. 비밀번호 변경은 다른 로그인 세션을 해제하고 현재 브라우저의 로그인을 유지합니다. 비밀번호 재설정은 전체 세션을 해제하므로 새 비밀번호로 다시 로그인해야 합니다. 메일 재설정 링크 발송은 SMTP 환경변수를 설정했을 때 활성화됩니다. SMTP가 없는 로컬 환경에서는 저장해 둔 복구 코드로 재설정할 수 있습니다.

카카오 로그인은 개발자 콘솔에서 앱 키와 리다이렉트 URI를 등록한 뒤 루트 `.env`에 앱 키를 채우면 활성화됩니다. 기본 리다이렉트 URI는 `APP_ORIGIN` 뒤에 `/api/auth/kakao/callback`을 붙여 자동으로 정하므로, 포트를 바꾸면 `APP_ORIGIN`만 실제 웹 주소로 맞추면 됩니다. 카카오 개발자 콘솔에도 같은 URI를 등록해야 합니다. 별도 주소가 필요하면 `KAKAO_REDIRECT_URI`에 명시할 수 있습니다. `.env.example`을 복사한 경우에는 필요한 키 이름이 들어 있습니다. 앱 키가 설정되지 않은 동안에는 로그인 화면에서 카카오 버튼이 비활성화되고, 이메일 로그인 안내가 표시됩니다. 카카오 로그인은 시작한 페이지의 같은 출처 경로와 검색 조건을 기억해 인증을 마친 뒤 돌아오며, 외부 사이트로 향하는 복귀 주소는 허용하지 않습니다.

```dotenv
KAKAO_CLIENT_ID=카카오_앱_REST_API_키
KAKAO_CLIENT_SECRET=사용하는_경우_카카오_시크릿
KAKAO_REDIRECT_URI=
AUTH_COOKIE_SECURE=false
APP_ORIGIN=http://localhost:5173
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USER=메일_계정
SMTP_PASSWORD=메일_앱_비밀번호
SMTP_FROM=문서담 <noreply@example.com>
```

`start-app.ps1`의 로컬 실행은 `.env`의 카카오·SMTP 설정을 읽습니다. Compose도 같은 변수를 API에 전달합니다. SMTP를 설정하지 않아도 가입과 로그인은 사용할 수 있으며, 비밀번호 찾기 화면에서 복구 코드 방식으로 재설정할 수 있습니다. HTTPS로 배포할 때는 `AUTH_COOKIE_SECURE=true`로 설정하고 `APP_ORIGIN`을 웹 주소에 맞춰 주세요.

웹은 문서 목록과 준비 상태를 별도로 불러옵니다. `/api/ready`가 로컬 모델에 실제 요청을 보내기 때문에, 페이지 진입과 사용자의 재시도 때만 모델 준비 확인을 실행합니다. 문서 목록을 먼저 표시해 모델 점검이 화면 로딩을 막지 않게 했습니다.

## Docker를 쓸 수 없는 PC에서 웹과 API 한 번에 실행

최초 한 번 Python과 웹 의존성을 준비한 뒤, 저장소 루트에서 다음 명령 하나로 SQLite API와 웹 개발 서버를 시작할 수 있습니다. Ollama가 실행되지 않은 경우 기존 모델이 있는 Ollama 설치본을 사용해 로컬 서비스를 시작합니다. 실행 중인 문서담 프로세스는 강제로 종료하지 않습니다. 요청한 API 포트에 기존 API가 있으면 OpenAPI 버전과 문서 목록 응답을 확인합니다. 문서 목록을 읽지 못하는 API는 재사용하지 않고 다음 빈 포트를 선택해 웹 프록시 주소를 맞춥니다. 설치된 모델만 검사하며, 없는 모델을 자동 다운로드하거나 다른 모델로 바꾸지 않습니다.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r server/requirements.txt
npm --prefix web ci  # 최초 한 번만 실행
.\scripts\start-app.ps1
```

웹 화면은 기본적으로 http://localhost:5173 에서 열립니다. 그 포트에 다른 서비스가 있으면 기존 프로세스는 유지하고 다음 빈 포트로 시작합니다. 실행이 끝나면 스크립트가 실제 웹 주소를 출력하므로 그 주소를 사용하세요. 시작 후 데이터베이스, Ollama, 두 지정 모델을 실제 호출해 상태를 출력합니다. 기본은 브라우저를 자동으로 띄우지 않으며, 필요하면 `-OpenBrowser`를 붙입니다. 포트를 직접 지정하려면 `-ApiPort` 또는 `-WebPort`를 사용하세요. 수동 개발 모드의 API 코드를 수정했다면 해당 터미널에서 `Ctrl+C`로 멈춘 뒤 다시 시작합니다.

## Docker를 쓸 수 없는 PC의 수동 로컬 개발 실행

Docker Desktop 서비스가 실행되지 않을 때는 API와 웹 화면을 각각 실행합니다.

최초 한 번, 프로젝트 루트에서 Python 환경을 준비합니다.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r server/requirements.txt
```

첫 번째 PowerShell에서 프로젝트 루트 기준으로 API를 시작합니다.

```powershell
./scripts/run-local.ps1
```

API 코드를 변경한 뒤에는 해당 터미널에서 `Ctrl+C`로 종료하고 같은 명령으로 다시 시작합니다.
8000 포트를 다른 프로그램이 점유한 경우 `./scripts/run-local.ps1 -ApiPort 8001`처럼 빈 포트를 지정할 수 있습니다. 실행 스크립트가 웹 개발 서버용 로컬 프록시 설정도 함께 기록합니다. 웹 기본 포트는 5173이며, 다른 프로그램이 사용 중이면 그 프로세스를 종료하지 말고 웹 시작 시 빈 포트를 지정하세요.

두 번째 PowerShell에서:

```powershell
cd web
npm ci  # 최초 한 번만 실행
npm run dev
```

웹 기본 주소는 http://localhost:5173 입니다. 이 포트가 이미 사용 중이면 기존 프로세스를 종료하지 말고, 웹 폴더에서 `npm run dev -- --port 5174`처럼 비어 있는 포트를 지정하세요. 브라우저에서는 실제로 시작된 주소를 엽니다. API 실행 스크립트는 기본 8000 포트를 확인하고 `-ApiPort`로 다른 포트를 지정하면 웹 프록시 주소도 맞춥니다. API는 SQLite 파일 DB와 Python 코사인 비교를 쓰는 로컬 개발 모드로 시작합니다. Ollama의 `qwen3:4b-instruct`와 `embeddinggemma`는 동일하게 로컬 호출하며 대체하지 않습니다. 이 실행 모드는 Compose의 PostgreSQL/pgvector 구성을 바꾸지 않으며, 업로드 파일과 DB는 `data/`에 저장됩니다. 로컬 개발 서버는 기본적으로 이 PC에서만 연결할 수 있습니다. 검색 집합이 커질수록 Python 벡터 비교가 느려지므로 배포 검증은 Compose 구성을 사용하세요.

각 터미널에서 `Ctrl+C`를 누르면 해당 개발 서버를 종료합니다.

## 회귀 테스트

저장소 루트에서 웹 회귀 테스트와 API 테스트를 각각 실행할 수 있습니다. 웹은 여러 문서 비교 답변, 정확한 시각 부재 안내, 내부 인용 표식 제거를 확인합니다. API는 가까운 검색 후보의 무관한 시각 규칙이 보류를 막지 않는지, 출장비 신청 표현이 정산 기한 근거로 연결되는지와 근거 없는 기한 추측을 차단하는지 검사합니다. 격리한 임시 SQLite에서 업로드·중복 차단·목록·상세·원본 받기·삭제 흐름, 클라이언트 파일 경로 제거와 잘못된 파일 거절도 확인합니다. PDF·DOCX·TXT 추출, 페이지·제목 위치 보존, 청크 분할과 텍스트가 없는 스캔 PDF 안내도 검사합니다. PDF와 DOCX는 메모리에서 만들고, 업로드 테스트의 DB와 파일은 임시 폴더에서 정리해 실제 자료실을 바꾸지 않습니다. 로컬 API 테스트는 저장소 루트에서 `.venv`의 Python 환경을 사용합니다.

```powershell
npm --prefix web test
```

API 응답 정리도 별도로 확인할 수 있습니다.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s server\tests -v
```

## 현재 구현 범위

- 이메일 가입·로그인, 세션 보호, 로그아웃, 비밀번호 변경·메일 재설정·복구 코드 재설정과 계정별 문서 접근 제어. 재설정 메일은 SMTP 설정이 필요하고, 카카오 로그인은 앱 키를 설정했을 때 사용할 수 있습니다.
- 문서 검색·내 문서·즐겨찾기·검색 기록·계정 관리·사용 안내·프로젝트 소개 화면을 제공하며, 각 화면은 주소로 다시 열 수 있습니다.
- 검색 기록은 계정별 브라우저에 최대 20개까지 보관합니다. 저장 공간을 사용할 수 있으면 다음 방문에도 이어지며, 브라우저 저장이 막힌 경우에는 현재 탭에서만 유지됩니다. 검색 기록 화면에서 질문·문서 이름을 검색하거나 답변·문서 검색 유형으로 좁힐 수 있고, 기록은 직접 지우거나 브라우저 데이터 삭제로 정리할 수 있습니다. 즐겨찾기와 최근 문서도 계정별 브라우저 저장소를 사용하며, 같은 브라우저의 다른 탭과 변경 내용을 동기화합니다.
- 문서가 등록되면 검색 홈을 문서 목록·업로드와 질문·답변이 이어지는 작업 공간으로 구성하고, 좁은 화면에서는 두 영역을 전환합니다. 전체 문서 필터와 관리 기능은 별도 문서함에서 제공합니다.
- 추출된 제목으로 문서 주제 바로가기를 제공하며, 주제를 누르면 해당 문서 범위를 선택하고 핵심 내용·근거를 묻는 질문 문장을 입력란에 채웁니다. 최근 문서와 즐겨찾기의 제목으로 검색 질문 예시도 구성해, 예시 클릭 시 문서 범위와 질문이 함께 설정됩니다. 모바일에서는 최근 문서와 즐겨찾기 목록 아래의 주제를 접어 두고 필요할 때 펼칠 수 있습니다. 문서함 행의 돋보기로도 상세 화면을 거치지 않고 문서 범위를 고를 수 있습니다.
- PDF, DOCX, TXT와 최대 20 MB 제한 검증
- 여러 파일 업로드를 순차 처리하고, 현재 파일·경과 시간·파일별 처리 결과 표시; 파일 처리 응답이 10분간 없으면 등록 여부를 다시 확인하도록 안내
- PDF 페이지별 텍스트 추출, 원문 순서를 유지하는 DOCX 본문·표와 제목 정보, UTF-8 TXT 추출
- 텍스트가 포함된 PDF 지원; 스캔 이미지 PDF의 OCR은 미지원
- 텍스트 구간 생성 및 문서 메타데이터 저장
- 문서 목록 및 삭제 (원본 파일과 구간 레코드 함께 삭제)
- 파일명·형식·처리 상태별 문서 필터와 날짜·이름 정렬. 상태 선택지에는 현재 파일명·형식·즐겨찾기 조건을 반영한 문서 수를 함께 표시
- 문서 재처리와 즐겨찾기 해제 후 키보드 초점을 목록의 유효한 항목으로 이어가고, 대량 선택은 Shift 범위 선택·부분 선택 표시를 지원하며 키보드로 선택 모드를 켜면 첫 체크박스에 초점을 이동
- 이 브라우저에 선택을 저장하는 즐겨찾기 모아보기와 문서함·즐겨찾기 20개 단위 페이지 이동
- 검색 결과와 문서함에서 열어본 문서를 브라우저에 기억해 작업 공간에서 다시 열기 (문서 ID만 저장, 삭제 시 정리, 기록 지우기 제공)
- 검색 근거 링크에 `#chunk-N` 원문 위치를 담아 주소 복사·새 탭·새로고침 후에도 같은 구간 열기 지원
- 삭제 전 문서 이름·영향 범위를 확인하는 키보드 조작 가능한 앱 내 확인 창
- 문서 상세 원문은 한 번에 40개 구간씩 불러오며, 원본 파일 내려받기 제공
- 12개를 넘는 구간이 있고 제목이 둘 이상인 문서는 추출된 제목 목차에서 원하는 원문 구간으로 바로 이동
- 검색 결과나 저장한 근거의 출처를 열면 해당 구간이 포함된 원문 페이지로 이동하고, 검색 당시 질문과 일치하는 단어도 찾아보기 쉽게 강조
- 문서 상세에서 현재 문서의 추출 텍스트 전체를 다시 찾아 관련 구간으로 이동
- 문서·검색 API 응답은 브라우저 캐시에 남지 않도록 설정
- 파일 내용의 SHA-256을 비교해 같은 문서의 중복 업로드를 안내
- 상태/오류 표시
- embeddinggemma 768차원 임베딩 생성과 pgvector 코사인 유사도 검색
- 검색 결과에 서버가 원문 문서 ID, 구간 ID, 페이지·제목, 구간 번호와 발췌문을 첨부
- 근거와 원문 구간을 문서명·페이지·제목 위치와 함께 복사하거나, 답변과 전체 출처를 한 번에 복사
- 검색 결과·답변·저장한 근거에서 “앞뒤 문맥 보기”를 열어 해당 구간과 이웃 구간을 확인. 저장한 근거에서 원문을 읽고 돌아오면 검색어, 정렬, 페이지와 펼쳐 둔 문맥을 복원
- 최근 검색 20개와 실행 시각은 계정별 브라우저 저장소에 보관하며, 검색 화면과 문서함에서 다시 실행하거나 개별·전체 삭제 가능. 선택 문서를 사용할 수 없으면 전체 범위로, 의미 검색이나 답변 기능이 중단되면 가능한 단어·근거 검색으로 이어가고 전환 이유를 안내. 진행 중인 검색어와 결과/답변 화면은 URL에 노출하지 않고 탭의 history state에 보관해 새로고침과 뒤로·앞으로 이동에서 복원
- 검색 결과와 답변의 근거 발췌를 계정별 브라우저에 최대 200개까지 저장하고, 문서·질문·발췌로 찾거나 최근 저장순·오래된 순·문서명순으로 정렬. 화면은 20개씩 나누어 보고, 현재 검색·정렬 조건에 맞는 전체 결과를 출처 링크와 함께 Markdown으로 내보낼 수 있습니다. 원문 문서가 삭제돼도 저장 발췌는 남고, 원문을 열 수 없다는 상태를 표시합니다.
- `Ctrl K`(Windows/Linux) 또는 `⌘ K`(macOS)로 어느 화면에서든 검색 입력란으로 이동
- 인덱싱 실패 후 수동 재시도; 지정 모델 부재 시 다른 모델로 대체하지 않음
- 검색 점수를 확률이나 정확도로 표시하지 않음
- 검색 근거로만 답변하고 문서 내부 지시문은 실행하지 않음
- 답변에 적힌 수치, 단위, 근무일·영업일 기준과 비교 조건을 인용한 원문에 대조. 확인되지 않으면 한 번 다시 생성하고, 같은 문제가 남으면 보류
- 두 주제가 결합된 질문은 각 부분을 따로 검색해 근거를 모으고, 한 부분이라도 출처를 연결하지 못하면 부분 답변을 보류
- 근거가 부족하면 답변과 출처를 비우고 보류
- 평가 세트로 Recall@5·답변 정답성·출처 정확도·보류 정확도·중앙 응답시간 측정

## 포트폴리오

파일 형식과 검색 사용법은 웹 앱의 `사용 안내`에서, 화면 흐름과 설계 선택, 평가 수치의 범위는 [프로젝트 사례 문서](portfolio-case-study.md)와 `프로젝트 소개` 화면에서 확인할 수 있습니다. 평가 문항 원본, 각 질문의 결과와 한계는 `evaluation/`에 보관합니다.

GitHub Actions는 push, pull request, 수동 실행에서 API 단위 테스트와 웹 테스트·프로덕션 빌드를 각각 확인합니다. CI는 SQLite 임시 DB와 모의 응답을 사용하는 테스트만 실행하므로 SMTP 계정, Kakao 키, Ollama 서버나 모델을 저장할 필요가 없습니다. 지정 Ollama 모델을 실제 호출하는 평가는 로컬에서 별도로 실행하며, 이 CI 통과를 모델 품질이나 배포 환경 검증으로 해석하지 않습니다.

로컬에서 CI와 같은 기본 검사를 실행하려면 프로젝트 루트와 `web` 폴더에서 각각 실행합니다.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r server/requirements.txt
.\.venv\Scripts\python.exe -m unittest discover -s server\tests -v
npm --prefix web ci
npm --prefix web test
npm --prefix web run build
```

## 골드 질문 평가

저장소가 비어 있어 기획서가 참조하는 36개 골드 질문 원본이 없었습니다. `evaluation/docs/`의 기획서 규칙 기반 가상 문서 3개와 `evaluation/gold_questions.json`의 18개 단일 근거·6개 복수 근거·12개 답변 불가 문항으로 재현 가능한 평가 구성을 만들었습니다. 12개 예시 질문은 `evaluation/dev_questions.json`에 따로 둡니다. 개발 세트는 임계값 확인에, 재구성 골드 세트는 개발 중 회귀 확인에도 사용했으므로 최신 결과는 독립 블라인드 평가가 아닙니다. 평가 방식과 한계는 `evaluation/README.md`와 프로젝트 사례 문서에 기록했습니다.

Python 가상환경에 API 의존성을 설치하고 Ollama에서 두 지정 모델을 준비한 뒤, 저장소 루트에서 실행합니다.

```powershell
.\.venv\Scripts\python.exe evaluation/run_evaluation.py --isolated --suite both
```

`--isolated`는 임시 SQLite와 가상 문서 3개로 FastAPI를 시작하고 평가가 끝나면 정리합니다. 개발 12문항과 골드 36문항 각각의 JSON 보고서가 `evaluation/results/`에 남습니다. 별도 PostgreSQL/pgvector 환경에서 측정하는 명령과 자동 채점의 한계는 [평가 안내](../evaluation/README.md)를 참고하세요.

텍스트 기반 PDF만 지원합니다. 스캔 이미지 PDF의 OCR은 기획서 MVP 범위에서 제외했습니다. 원본은 Compose의 `uploads` 볼륨에, 메타데이터와 구간은 `postgres_data` 볼륨에 저장됩니다.
